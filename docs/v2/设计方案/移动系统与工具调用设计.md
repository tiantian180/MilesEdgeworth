# 移动系统与工具调用设计

本文档定义 MilesEdgeworth v2 中桌宠目标点移动和 Go sidecar 工具调用的设计。它是长期维护文档，指导 MotionController 架构、sidecar tool use 骨架、`pet_motion` tool 协议和 ChatController 集成。

相关文档分工：

- `桌宠运行时与动画调度设计.md`：PetRuntime 调度模型、PetState、移动系统概念模型。
- `桌宠运行时职责拆分设计.md`：MotionController 类边界和依赖方向。
- `AI 聊天动画编排设计.md`：ChatController 状态机和动画-文字同步。
- `总体架构设计.md`：模块边界和通信协议总览。

## 1. 设计目标

让模型可以通过工具调用请求桌宠移动到屏幕指定位置或相对移动一段距离。

具体要求：

- 模型通过 **OpenAI-compatible tool use** 协议请求移动，不使用文本标记。
- **移动和说话互斥**：模型在同一条消息中输出文字 + tool_call 时，桌宠先说完文字、播完动画，再执行移动。
- 移动期间桌宠播放对应方向的走/跑动画，到达目标后自然回 idle。
- **用户拖拽立即打断移动**，tool result 回传"被用户打断"，模型可以自然回应。
- 坐标使用**屏幕百分比**（0.0~1.0），Qt 侧负责解析为实际像素。
- Go sidecar 的 tool use 骨架是通用的，`pet_motion` 是第一个 tool，后续 Phase 可以注册更多 tool。

非目标：

- 不做自由漫游（wander）。随机漫步继续由 BehaviorTriggerEngine 的 `idle.loopFinished` / `action.completed` 触发。
- 不做路径规划、避障或多屏寻路。
- 不做 gRPC / WebSocket 通信协议替换。
- 不做通用 agent harness、MCP 或插件系统。

## 2. 通信协议扩展

### 2.1 当前通信模型

```
Qt ──POST /v1/chat/messages──> Sidecar ──> Provider
Qt <──SSE stream (同一连接)─── Sidecar <── Provider
```

Qt 发一次 POST，sidecar 在同一 HTTP 连接上持续推 SSE 事件。单向请求-流式响应。

### 2.2 Tool use 扩展

模型输出 `tool_calls` 时，sidecar 需要暂停流式输出、通知 Qt 执行 tool、等待结果后继续。这引入了一个新的通信方向：Qt → sidecar 回传 tool 结果。

```
Qt ──POST /v1/chat/messages────> Sidecar         (原有)
Qt <──SSE: TOOL_CALL event─────── Sidecar         (新增)
Qt ──POST /v1/chat/tool-result──> Sidecar         (新增)
Qt <──SSE: 继续流式响应─────────── Sidecar         (原有连接)
```

原始 SSE 连接在 tool 执行期间保持打开。Sidecar 内部用 Go channel 等待 tool result，收到后继续与 provider 交互并在同一 SSE 流上推送后续事件。

### 2.3 新增 HTTP 端点

```
POST /v1/chat/tool-result
Content-Type: application/json

{
  "runId": "r1",
  "toolCallId": "tc1",
  "result": { ... }
}
```

Sidecar 收到后将 tool result 作为 `tool` role message 发回 provider，继续生成。

### 2.4 SSE 事件序列

事件类型必须与项目已有协议一致：`RUN_STARTED`、`TEXT_MESSAGE_START`、`TEXT_MESSAGE_CONTENT`、`TEXT_MESSAGE_END`、`RUN_FINISHED`、`RUN_ERROR`、`CUSTOM`。

Tool call 使用 sidecar 聚合后的 compact event `TOOL_CALL`。OpenAI streaming 中 tool_calls 参数是分片流出的，sidecar 在 provider 层内部聚合完整 `function.name` + `function.arguments` 后，对 Qt 发一个完整的 `TOOL_CALL` 事件，而不是 AG-UI 的三段 `TOOL_CALL_START/ARGS/END`。这样 Qt 侧解析更简单，且 sidecar 可以在 emit 前校验 JSON 参数格式。

正常 tool 调用场景（模型先说话再移动）：

```
event: RUN_STARTED
data: {"type":"RUN_STARTED","runId":"r1"}

event: CUSTOM
data: {"type":"CUSTOM","name":"miles.pet.lifecycle","runId":"r1","value":{"state":"thinking"}}

event: TEXT_MESSAGE_START
data: {"type":"TEXT_MESSAGE_START","runId":"r1","messageId":"m1","role":"assistant"}

event: CUSTOM
data: {"type":"CUSTOM","name":"miles.pet.expression.requested","runId":"r1","value":{"expression":"polite"}}

event: TEXT_MESSAGE_CONTENT
data: {"type":"TEXT_MESSAGE_CONTENT","runId":"r1","messageId":"m1","delta":"好的，我走过去看看。"}

event: TEXT_MESSAGE_END
data: {"type":"TEXT_MESSAGE_END","runId":"r1","messageId":"m1"}

event: TOOL_CALL
data: {"type":"TOOL_CALL","runId":"r1","toolCallId":"tc1","toolName":"pet_motion","toolArgs":"{\"action\":\"moveTo\",\"x\":0.8,\"y\":0.9,\"mode\":\"walk\"}"}

... Qt: 文字吐完 → 动画 cleanFinish → MotionController 执行移动 → POST tool-result ...
... sidecar 将 tool result 发回 provider，provider 继续生成 ...

event: TEXT_MESSAGE_START
data: {"type":"TEXT_MESSAGE_START","runId":"r1","messageId":"m2","role":"assistant"}

event: CUSTOM
data: {"type":"CUSTOM","name":"miles.pet.expression.requested","runId":"r1","value":{"expression":"neutral"}}

event: TEXT_MESSAGE_CONTENT
data: {"type":"TEXT_MESSAGE_CONTENT","runId":"r1","messageId":"m2","delta":"嗯，这里不错。"}

event: TEXT_MESSAGE_END
data: {"type":"TEXT_MESSAGE_END","runId":"r1","messageId":"m2"}

event: RUN_FINISHED
data: {"type":"RUN_FINISHED","runId":"r1"}
```

模型只调用 tool 不说话的场景：

```
event: RUN_STARTED
data: {"type":"RUN_STARTED","runId":"r1"}

event: CUSTOM
data: {"type":"CUSTOM","name":"miles.pet.lifecycle","runId":"r1","value":{"state":"thinking"}}

event: TOOL_CALL
data: {"type":"TOOL_CALL","runId":"r1","toolCallId":"tc1","toolName":"pet_motion","toolArgs":"{\"action\":\"moveTo\",\"x\":0.5,\"y\":0.5,\"mode\":\"run\"}"}

... Qt: cleanFinish thinking 动画 → 执行移动 → POST tool-result ...

event: TEXT_MESSAGE_START
data: {"type":"TEXT_MESSAGE_START","runId":"r1","messageId":"m2","role":"assistant"}

event: TEXT_MESSAGE_CONTENT
data: {"type":"TEXT_MESSAGE_CONTENT","runId":"r1","messageId":"m2","delta":"到了！"}

event: TEXT_MESSAGE_END
data: {"type":"TEXT_MESSAGE_END","runId":"r1","messageId":"m2"}

event: RUN_FINISHED
data: {"type":"RUN_FINISHED","runId":"r1"}
```

注意：每次 provider 调用产生独立的 `TEXT_MESSAGE_START/END` 对（messageId 不同），但整个对话只有一对 `RUN_STARTED/FINISHED`。

## 3. Go sidecar tool use 骨架

### 3.1 Provider 层变化

`ChatParams` 新增 `Tools` 字段：

```go
type ToolDefinition struct {
    Name        string          `json:"name"`
    Description string          `json:"description"`
    Parameters  json.RawMessage `json:"parameters"`
}

type ChatParams struct {
    ConversationID     string
    RunID              string
    MessageID          string
    Operation          string
    Messages           []Message
    KnownExpressionIDs []string
    Tools              []ToolDefinition    // 新增
}
```

`openai.Provider.StreamChat` 在请求体中附加 `tools` 字段（OpenAI-compatible 格式）。流式响应中 tool_calls 参数通过 `choice.delta.tool_calls` 分片流出，Provider 内部逐 chunk 聚合 `function.name` + `function.arguments`，在流结束（`finish_reason == "tool_calls"` 或 `[DONE]`）后 emit 聚合完成的 `TOOL_CALL` 事件。

**生命周期事件职责拆分**：当前 Provider `pipe()` 自行 emit `RUN_STARTED` / `TEXT_MESSAGE_START` / `TEXT_MESSAGE_END` / `RUN_FINISHED` 等完整生命周期。引入 tool 循环后，一个 run 可能多次调用 Provider。为避免重复 emit，生命周期事件的所有权需要上移：

- **Service/API 层**拥有 `RUN_STARTED` / `RUN_FINISHED` / `RUN_ERROR`：整个 run 只 emit 一次。
- **Provider 层**只产出内容事件（`TEXT_MESSAGE_START/CONTENT/END`、`TOOL_CALL`、`CUSTOM`）和错误。
- Provider 新增 continuation 模式：tool result 后的第二次调用不再 emit `RUN_STARTED` / lifecycle thinking，因为 run 已经在进行中。

### 3.2 StreamEvent 扩展

```go
type StreamEvent struct {
    Type       string         `json:"type"`
    Name       string         `json:"name,omitempty"`
    RunID      string         `json:"runId,omitempty"`
    MessageID  string         `json:"messageId,omitempty"`
    Role       string         `json:"role,omitempty"`
    Delta      string         `json:"delta,omitempty"`
    RawDelta   string         `json:"-"`
    Value      map[string]any `json:"value,omitempty"`
    Error      string         `json:"error,omitempty"`
    ToolCallID string         `json:"toolCallId,omitempty"`  // 新增
    ToolName   string         `json:"toolName,omitempty"`    // 新增
    ToolArgs   string         `json:"toolArgs,omitempty"`    // 新增，JSON string
}
```

新增 event type：

- `TOOL_CALL`：模型请求调用 tool。

### 3.3 Tool 定义与注册

Sidecar 启动时注册可用 tools。Phase 2.5 只注册 `pet_motion`：

```go
var PetMotionTool = ToolDefinition{
    Name:        "pet_motion",
    Description: "控制桌宠移动。moveTo 移到屏幕百分比坐标，moveBy 相对当前位置移动。",
    Parameters:  json.RawMessage(`{...}`),  // 见 §4.1
}
```

Tool 定义在 chat service 层管理，不在 provider 层。Service 在构建 ChatParams 时注入当前可用 tools。

### 3.4 Tool 执行循环

```
Service.StreamChat():
  0. emit RUN_STARTED + lifecycle thinking
  1. 构建 messages + tools → provider.StreamChat(continuation=false)
  2. 逐事件转发到 SSE output channel（Provider 只产出 content/tool/custom 事件）
  3. 收到 TOOL_CALL 事件：
     a. emit TOOL_CALL 到 SSE
     b. 等待 toolResultChan (由 HTTP handler 写入)
     c. 收到 result → 追加 assistant tool_calls message + tool result message 到 messages
     d. 再次调用 provider.StreamChat(continuation=true)
        （continuation 模式：Provider 不 emit lifecycle thinking，因为 run 已在进行）
     e. 回到步骤 2
  4. Provider 流正常结束（无更多 tool_calls）→ emit RUN_FINISHED → 结束
```

Tool 执行循环上限：每次对话最多 3 轮 tool 调用，防止无限循环。超过上限时 Service emit `RUN_ERROR`。

生命周期事件只出现一次：`RUN_STARTED` 在步骤 0，`RUN_FINISHED` 在步骤 4。`TEXT_MESSAGE_START/END` 每次 Provider 调用各出现一次（tool result 后的续接是新 message）。

## 4. pet_motion tool

### 4.1 参数 schema

```json
{
  "type": "object",
  "properties": {
    "action": {
      "type": "string",
      "enum": ["moveTo", "moveBy"],
      "description": "moveTo: 移到屏幕可达区域百分比坐标; moveBy: 相对当前位置移动"
    },
    "x": {
      "type": "number",
      "description": "moveTo: 可达区域百分比 x (0.0=最左, 1.0=最右); moveBy: 相对位移百分比 (正值=向右)"
    },
    "y": {
      "type": "number",
      "description": "moveTo: 可达区域百分比 y (0.0=最上, 1.0=最下); moveBy: 相对位移百分比 (正值=向下)"
    },
    "mode": {
      "type": "string",
      "enum": ["walk", "run"],
      "description": "移动速度模式，默认 walk"
    }
  },
  "required": ["action", "x", "y"]
}
```

Phase 2.5 不暴露 `stop` action 给模型。理由：移动与说话互斥，模型在 tool 执行期间无法再发 tool_call；用户可以通过拖拽打断。`stop()` 作为 MotionController 内部方法保留（供取消路径使用），但不注册为 tool 参数。

### 4.2 坐标系

**可达区域百分比**坐标，左上角 (0.0, 0.0)，右下角 (1.0, 1.0)。可达区域 = 屏幕尺寸减去桌宠窗口尺寸，保证百分比 1.0 意味着桌宠完全可见并靠边。

Qt 侧坐标转换：

```
scaledWindowSize = petWindowSize × petScale
reachableWidth  = screen.width  - scaledWindowSize
reachableHeight = screen.height - scaledWindowSize

moveTo(x, y):
  targetPixel.x = screen.x + x × reachableWidth
  targetPixel.y = screen.y + y × reachableHeight

moveBy(dx, dy):
  targetPixel.x = currentPosition.x + dx × reachableWidth
  targetPixel.y = currentPosition.y + dy × reachableHeight
```

result 中返回的百分比坐标也基于可达区域计算：

```
resultX = (currentPixel.x - screen.x) / reachableWidth
resultY = (currentPixel.y - screen.y) / reachableHeight
```

这样 `(0.0, 0.0)` = 左上角、`(1.0, 1.0)` = 右下角、`(0.5, 0.5)` = 屏幕中央，且桌宠始终完全可见。moveBy 的 delta 也基于可达区域宽高，语义一致。

### 4.3 Result schema

成功到达：

```json
{
  "success": true,
  "position": {"x": 0.8, "y": 0.9}
}
```

被用户拖拽打断：

```json
{
  "success": false,
  "reason": "interrupted_by_user",
  "position": {"x": 0.45, "y": 0.6}
}
```

边界夹取后到达（moveBy 目标超出可达范围，实际到达边缘）：

```json
{
  "success": true,
  "position": {"x": 1.0, "y": 0.9},
  "note": "clamped_to_screen_edge"
}
```

`position` 始终返回移动结束时的百分比坐标，让模型知道桌宠最终在哪。

## 5. MotionController

### 5.1 类职责与接口

MotionController 负责目标点移动的计算和驱动。它不直接操作窗口，只输出运动意图（位置、方向），由 PetRuntime / DesktopShellController 执行实际窗口移动。

归属：PetRuntime 持有 MotionController（与 AudioController、PropController 同级）。

文件位置：`apps/desktop/src/pet/motion/MotionController.h`、`apps/desktop/src/pet/motion/MotionController.cpp`。

```cpp
struct MotionConfig {
    double walkSpeed = 60.0;    // 像素/秒, scale=1 基准
    double runSpeed = 120.0;
    double snapDistance = 5.0;  // 像素, scale=1 基准
    double petScale = 1.0;
    double petWindowSize = 120.0; // scale=1 基准窗口尺寸
    QStringList availableDirections; // manifest movementDirections
};

class MotionController : public QObject {
    Q_OBJECT
public:
    enum class State { Idle, Moving };

    void configure(const MotionConfig &config);
    void setScreenGeometry(const QRect &screenGeometry);
    void setCurrentPosition(const QPoint &petWindowPosition);

    void moveTo(double x, double y, const QString &mode);
    void moveBy(double dx, double dy, const QString &mode);
    void stop();

    State state() const;
    bool isMoving() const;

    void cancelForDrag();

signals:
    void started(const QString &movementDirection, const QString &mode);
    void positionChanged(const QPoint &newPosition);
    void directionChanged(const QString &newDirection);
    void completed(double finalX, double finalY);
    void interrupted(const QString &reason);
};
```

`MotionConfig` 由 PetRuntime 在加载 manifest 时、换肤时或 petScale 变化时注入。MotionController 不依赖 PetRuntime、SkinManifest 或 QML——它只依赖配置数据。

### 5.2 状态机

```
Idle ──moveTo/moveBy──> Moving
    ├── emit started(direction, mode)
    └── PetRuntime 收到信号后 playLocomotion()

Moving ──到达目标──> Idle
    ├── emit completed(finalX, finalY)
    └── PetRuntime 收到信号后 returnToIdle()

Moving ──cancelForDrag()──> Idle
    ├── emit interrupted("drag")
    └── PetRuntime 由拖拽流程自行管理动画

Moving ──stop()──> Idle
    ├── emit interrupted("stop")
    └── PetRuntime 收到信号后 returnToIdle()
```

在 Idle 状态下调用 stop() 是 no-op。在 Moving 状态下调用 moveTo/moveBy 会更新目标（不重新 emit started，只在方向变化时 emit directionChanged）。

### 5.3 QTimer tick 模型

MotionController 内部持有 QTimer，频率约 16ms（~60fps）。

每 tick：

1. 计算 current → target 的方向向量。
2. 量化为 8 方向（见 §5.5）。
3. 按 `speed × deltaTime` 沿方向向量移动。deltaTime 使用 `QElapsedTimer` 实测值，不假设固定 16ms。
4. 如果距离目标 < `snapDistance`，吸附到目标点并停止。
5. emit `positionChanged(newPosition)`。
6. 方向变化时 emit `directionChanged(newDirection)`。

Timer 在 `moveTo`/`moveBy` 时启动，在到达目标/打断/stop 时停止。Idle 状态下 timer 不运行。

### 5.4 速度与 manifest 配置

manifest 新增 `motion` 节：

```json
{
  "motion": {
    "walkSpeed": 60,
    "runSpeed": 120,
    "snapDistance": 5
  }
}
```

- `walkSpeed` / `runSpeed`：像素/秒，scale=1 基准。实际速度 = `baseSpeed × petScale`。
- `snapDistance`：像素，scale=1 基准。距离目标小于此值时吸附。

`SkinManifestLoader` 解析 `motion` 节；未声明时使用上述默认值。

PetRuntime 在初始化 MotionController 时注入速度参数。换肤时更新。

### 5.5 方向量化

计算 current → target 的角度（`atan2`），映射到 manifest 声明的 `movementDirections` 中最近的方向。

Miles 皮肤 8 方向角度映射。角度使用 `atan2(-dy, dx)` 计算（屏幕坐标 Y 轴向下，取反后转为数学坐标系），从 east (0°) 开始逆时针递增：

| 方向 | 角度范围 |
|------|---------|
| east | -22.5° ~ 22.5° |
| northEast | 22.5° ~ 67.5° |
| north | 67.5° ~ 112.5° |
| northWest | 112.5° ~ 157.5° |
| west | 157.5° ~ 180° 和 -180° ~ -157.5° |
| southWest | -157.5° ~ -112.5° |
| south | -112.5° ~ -67.5° |
| southEast | -67.5° ~ -22.5° |

方向变化时，PetRuntime 通过 `directionChanged` 信号调用 `playLocomotion` 切换走/跑动画变体，并通过 `updateFacingFromMovementDirection` 更新朝向。

### 5.6 边界处理

MotionController 负责目标位置的 clamp。`DesktopShellController` 不再对 MotionController 产出的 `positionChanged` 做二次 clamp——MotionController 保证输出的位置已在可达范围内。

可达范围（桌宠完全可见）：

```
scaledWindowSize = config.petWindowSize × config.petScale
minX = screenGeometry.x
minY = screenGeometry.y
maxX = screenGeometry.x + screenGeometry.width - scaledWindowSize
maxY = screenGeometry.y + screenGeometry.height - scaledWindowSize
```

如果 moveTo/moveBy 的目标被 clamp，到达 clamp 后的位置后正常完成，result 中附加 `"note": "clamped_to_screen_edge"`。

注：`DesktopShellController` 仍保留对用户拖拽和随机漫步（`consumeFrameMovementDelta`）的边界夹取。两套 clamp 各管各的移动源，不互相干涉。

### 5.7 拖拽打断

`PetEventBridge.submitDragStarted()` 调用 `MotionController.cancelForDrag()`：

1. 如果 MotionController 不在 Moving 状态，cancelForDrag 是 no-op。
2. 如果在 Moving 状态，立即停止 timer，设为 Idle，emit `interrupted("drag")`。
3. 拖拽期间的动画和移动由原有拖拽流程管理（GestureTracker + InteractionPipeline），不经过 MotionController。

### 5.8 与现有随机漫步的关系

当前的随机走/跑由 `BehaviorTriggerEngine` 通过 `idle.loopFinished` / `action.completed` 触发。这些移动使用 `consumeFrameMovementDelta()`，速度与 GIF 帧率绑定。

MotionController 的目标点移动使用独立 QTimer，速度与帧率解耦。两套移动机制互不干涉。

MotionController 执行移动时，PetRuntime 保存进入移动前的 `autoMovementEnabled` 值，并临时设置为 `false` 暂停随机漫步。移动完成或打断后恢复进入移动前的 `autoMovementEnabled` 值，不覆盖用户通过菜单设置的偏好。

## 6. ChatController 集成

### 6.1 状态机扩展

Phase 2.4 已有状态：

```
IDLE → BUFFERING_FOR_START → STREAMING → GATED → WAITING_FOR_ANIMATION_END → IDLE
```

Phase 2.5 新增 `EXECUTING_TOOL` 状态，可从两个路径进入：

```
IDLE
  → BUFFERING_FOR_START
    ├── 收到 TEXT_MESSAGE_START → STREAMING
    │     → GATED（等 segment drain + cleanFinish）
    │       ├── 正常路径 → 继续 STREAMING
    │       └── 收到 TOOL_CALL → EXECUTING_TOOL
    └── 收到 TOOL_CALL（tool-only，无文字内容） → EXECUTING_TOOL
  EXECUTING_TOOL
    → BUFFERING_FOR_START（sidecar 继续推事件）→ ...
  GATED → WAITING_FOR_ANIMATION_END → IDLE
```

### 6.2 TOOL_CALL 处理流程

TOOL_CALL 可在两种状态下到达：

**路径 A：STREAMING/GATED 状态**（模型先输出文字再调 tool）：

1. 如果有 pending 文字，等待 segment 全部流出（pacer drain）。
2. 等待当前 expression 动画 cleanFinish。
3. 进入 `EXECUTING_TOOL` 状态。

**路径 B：BUFFERING_FOR_START 状态**（模型直接调 tool，不输出文字）：

1. 停止 start timeout（BUFFERING_FOR_START 的超时定时器）。
2. 等待 thinking 动画 cleanFinish（lifecycle thinking 在 BUFFERING_FOR_START 阶段已开始播放）。
3. 进入 `EXECUTING_TOOL` 状态。

进入 `EXECUTING_TOOL` 后，两条路径的处理一致：

4. 解析 `toolArgs`（action, x, y, mode）。
5. 如果 `toolName == "pet_motion"` 且 `action` 为 `moveTo` 或 `moveBy`：
   - 调用 `PetRuntime.requestMotion(action, x, y, mode)`。
   - 连接 `MotionController::completed` / `interrupted` 信号。
6. 如果 `toolName` 未知或参数无效：
   - 直接 POST tool result `{success: false, error: "unknown tool"}` 到 sidecar。
   - 不进入 EXECUTING_TOOL 状态，继续等待后续事件。

### 6.3 移动完成回调

```
MotionController::completed(finalX, finalY)
  → ChatController 构建 tool result:
    {"success": true, "position": {"x": finalX, "y": finalY}}
  → POST /v1/chat/tool-result
  → 状态从 EXECUTING_TOOL → BUFFERING_FOR_START

MotionController::interrupted(reason)
  → ChatController 构建 tool result:
    {"success": false, "reason": "interrupted_by_user", "position": {...}}
  → POST /v1/chat/tool-result
  → 状态从 EXECUTING_TOOL → BUFFERING_FOR_START
```

### 6.4 移动-聊天互斥

`EXECUTING_TOOL` 期间：

| 事件 | 处理 |
|------|------|
| 用户发新消息 | 输入框禁用，不接受新消息 |
| 用户点取消 | 停止移动 + 取消当前 chat session（同 Phase 2.4 取消路径，见 §9.2） |
| 用户拖拽桌宠 | `MotionController.cancelForDrag()` → interrupted → POST tool result → 继续对话 |
| Qt motion timeout（90s） | `MotionController.stop()` → interrupted("timeout") → POST tool result → 继续对话（见 §9.1） |
| SSE 流新事件 | 正常情况下 sidecar 在等 tool result，不会推新事件。如果因网络延迟收到残留事件，ChatController 缓存到状态恢复后处理 |

### 6.5 UI 表现

`EXECUTING_TOOL` 期间：

- 聊天窗口输入框**禁用**，placeholder 文字改为"Miles 正在移动…"。
- 不显示 typing indicator（桌宠不在"思考"，而是在"执行"）。
- 取消按钮仍然可用。

### 7.5 移动状态管理（enterMovingState / exitMovingState）

**问题 1**：`setState("moving")` 会走 `actionForState()` 查找 manifest 中的 `moving` state 定义，触发 `playAction`。但目标移动时 locomotion 动画由 `playLocomotion()` 播放，不应由 `setState` 的 `playAction` 副作用覆盖。而且 manifest 中可能没有名为 `moving` 的 state 定义，会 fallback 到 idle。

**问题 2**：manifest 中 `walk`/`run` action 的 `loopMode` 是 `onceThenIdle`——GIF 播完一遍后 `handleAnimationFinished` 检查 `m_currentAutoReturnToIdle == true`，触发 `setState("idle")` 回到站立。在帧驱动随机漫步中这是正确行为（走一步就停），但目标移动需要持续循环走路动画直到到达目标。

**方案**：PetRuntime 新增 `enterMovingState()` / `exitMovingState()` 方法，不调用 `setState()`：

```
enterMovingState():
  1. 如果尚未保存本次移动快照，保存 m_autoMovementEnabled 到 m_autoMovementEnabledBeforeMotion
  2. m_currentState = "moving"           // 只更新状态标签（不触发 playAction）
  3. emit currentStateChanged()
  4. m_suppressAutoIdle = true            // 抑制 autoIdle timer
  5. m_motionLoopOverride = true          // 新增标志位，见下文
  6. m_autoMovementEnabled = false        // 暂停随机 frame movement
```

```
exitMovingState():
  1. m_motionLoopOverride = false
  2. m_suppressAutoIdle = false
  3. m_autoMovementEnabled = m_autoMovementEnabledBeforeMotion
  4. 清除本次移动的 autoMovement 快照
  5. // m_currentState 由后续 returnToIdle() / setState("idle") 或拖拽流程更新
```

**locomotion 循环机制（`m_motionLoopOverride`）**：

`playLocomotion()` 在目标移动场景下需要让 `walk`/`run` 动画持续循环，而不是播一遍就停。做法是：`playLocomotion()` 内部检查 `m_motionLoopOverride`，如果为 true，在调用 `playAction` 前临时将 action 的 `loopMode` override 为 `"loop"`。具体：

```
playLocomotion(actionId, direction):
  1. 更新方向和朝向（现有逻辑不变）
  2. if (m_motionLoopOverride):
       setCurrentPhase(actionId, "single", phase{loopMode="loop", variant=...})
     else:
       playAction(actionId)  // 使用 manifest 原始 loopMode
```

`setCurrentPhase` 接收 `PhaseDefinition`，其 `loopMode` 字段决定播放行为。传入 `"loop"` 后，`m_currentAutoReturnToIdle` 被设为 false（因为只有 `onceThenIdle` 才是 true），GIF 会循环播放。`handleAnimationFinished` 在 `m_currentAutoReturnToIdle == false` 且无 recipe、无 pending request 时不会做任何事情，动画自然循环。

方向变化时 `directionChanged` 信号触发新的 `playLocomotion()`，同样 override loopMode，切换到新方向的循环 GIF。

MotionController 完成或被打断后，`exitMovingState()` 清除 `m_motionLoopOverride`，后续 `returnToIdle()` 正常执行。

这样：
- 不与 manifest `states` 模型冲突——`moving` 不需要作为 manifest state 定义
- locomotion 动画真正循环播放，不会播一遍就定帧或回 idle
- manifest 中 `walk`/`run` 的 `loopMode: "onceThenIdle"` 不需要修改——随机漫步仍按原有行为运行
- `m_currentState` 仍然更新为 `"moving"`，外部可读取当前状态

## 8. Go sidecar Message 模型扩展

当前 `chat.Message` 只有 `Role` + `Content` 两个字段，不支持 tool use 循环中需要的 `tool_calls`（assistant 角色）和 `tool` role message。需要扩展：

```go
type ToolCallFunction struct {
    Name      string `json:"name"`
    Arguments string `json:"arguments"`
}

type ToolCall struct {
    ID       string           `json:"id"`
    Type     string           `json:"type"` // "function"
    Function ToolCallFunction `json:"function"`
}

type Message struct {
    Role       string     `json:"role"`
    Content    string     `json:"content"`
    ToolCalls  []ToolCall `json:"tool_calls,omitempty"`  // assistant 消息中的 tool 调用
    ToolCallID string     `json:"tool_call_id,omitempty"` // tool role 消息的关联 ID
}
```

tool 执行循环中的 messages 追加示例：

```
// 初始对话 messages
[user] "帮我走到右边"

// provider 返回 assistant message with tool_calls
[assistant] content="好的" tool_calls=[{id:"tc1", function:{name:"pet_motion", arguments:"{...}"}}]

// Qt 返回 tool result 后，追加 tool role message
[tool] tool_call_id="tc1" content="{\"success\":true,\"position\":{\"x\":0.8,\"y\":0.9}}"

// 再次调用 provider，它看到完整的 tool use 上下文
```

`openai.Provider` 在构建 OpenAI API 请求时，将 `Message.ToolCalls` 序列化为 `tool_calls` 字段，`tool` role message 使用 `tool_call_id` 关联。这是 OpenAI-compatible 的标准格式。

## 9. Tool result 等待：超时与取消

### 9.1 双层超时

为保证"移动和说话互斥"不被打破，采用 Qt 侧 motion timeout < sidecar tool result timeout 的双层超时策略：

**Qt 侧 motion timeout（90 秒）**：ChatController 在进入 EXECUTING_TOOL 时启动定时器。超时后：

1. 调用 `MotionController.stop()`，触发 `interrupted("timeout")`。
2. 构建 tool result `{"success": false, "reason": "timeout", "position": {...}}`。
3. POST tool result 到 sidecar。
4. 状态正常回到 BUFFERING_FOR_START，等待后续事件。

这确保 Qt 侧始终主动回传 result，sidecar 不会在 Qt 还在移动时自行续接。

**Sidecar tool result timeout（120 秒）**：作为兜底安全网。正常情况下 Qt 侧 90 秒超时已经回传了 result，sidecar 不会触发此超时。只在 Qt 崩溃、网络断连等异常情况下生效：

1. Service 向 provider 发送超时 tool result：`{"success": false, "reason": "timeout"}`
2. Provider 继续生成（模型看到超时信息，可以自然回应）
3. 正常完成 run（RUN_FINISHED）

两个超时值可通过各自配置调整，不暴露给模型。关键不变量：**Qt motion timeout < sidecar tool result timeout**。

### 9.2 请求取消（context cancel）

用户在 EXECUTING_TOOL 状态点击取消按钮时：

1. ChatController 调用 `MotionController.stop()`，触发 interrupted("stop")。
2. ChatController 不 POST tool result，直接关闭 SSE 连接。
3. Sidecar 检测到连接关闭（request context cancel），清理 channel，终止 provider 调用。
4. 整个 run 以无 RUN_FINISHED 的方式结束（同 Phase 2.4 现有取消路径）。

### 9.3 toolResultChan 清理

`toolResultChan` 是 per-run 的 Go channel（`chan ToolResult`，buffered size 1）。生命周期：

- 创建：Service.StreamChat 进入 tool 等待时创建。
- 写入：HTTP handler POST /v1/chat/tool-result 通过 runID 查找 channel 写入。
- 关闭：run 结束（正常完成、超时、或 context cancel）时关闭并从 registry 移除。

registry 使用 `sync.Map`（key = runID），确保并发安全。过期 tool result（run 已结束后的 POST）返回 HTTP 404。
